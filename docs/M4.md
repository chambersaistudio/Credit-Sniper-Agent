# M4: three-bureau extraction and evidence relationships

Updated November 17, 2026. Active branch remains
`claude/credit-dispute-agent-u0yyq3`; the GitHub default branch is older.

## First implementation checkpoint

- Read-only version 1 evidence graph at `GET /api/accounts/evidence-graph`.
  Identity comes from the authenticated user; loading a profile scopes every
  node and relationship to that user. Mixed-owner pure-function inputs fail.
- Original-creditor and collector tradelines remain separate canonical accounts.
  A reported `original_creditor` or `sold_to` can suggest a relationship;
  corroborating fields and exact report/record/bureau/page references travel
  with it. Missing field provenance is explicit and never guessed.
- Relationships use only current VERIFIED records and are always review leads,
  not automatic dispute grounds. Multiple possible original accounts remain
  ambiguous. A conflicting original creditor prevents a debt-buyer-name match.
- The account detail page shows related accounts and their supporting fields.
  No relationship is fed into claim generation or mailing at this checkpoint.
- Canonical matching now refuses to choose silently between candidates within
  0.05 confidence of the top auto-link score. Existing links are not rewritten;
  re-linking historical records requires a separately audited migration plan.
- Truth-draft job results now return count-only gate summaries even when
  extraction quality fails, preventing account values from entering job listings.
- Hosted operator truth editing now permits PUT preflight from configured CORS
  origins. Authentication and operator allowlists are unchanged.
- The batch extractor now explicitly preserves payment standing embedded in raw
  status. This instruction was present only in the full-report prompt before.

The Mission Lane/TAB Bank label alias is restricted to relationship review,
not identity merging. Its brand/issuer basis was checked against
[Mission Lane legal disclosures](https://www.missionlane.com/legal) and
[the TAB Bank cardholder agreement](https://www.missionlane.com/legal/the-mission-lane-visa-credit-card-issued-by-transportation-alliance-bank-inc-dba-tab-bank).
This does not prove which individual account a collection belongs to.

## Validation boundaries

Synthetic fixtures exercise the Mission Lane/Jefferson Capital relationship,
unrelated Jefferson debts, ambiguous original accounts, unverified evidence,
source references, immutability, deterministic graph order and tenant isolation.
Three-bureau scaled-merge contract tests preserve raw monthly money/remarks and
provenance. These are not independent extraction benchmarks of real PDFs.

The pre-existing suite had stale Stage-3 schema/plan fixtures, fake batch
provenance and operator-operation inventories. Repairs preserve strict gates;
they do not weaken production provenance or authorization requirements.

## Remaining M4 exit gates

1. Obtain an authenticated operator session through secure sign-in, or an
   existing securely provisioned operator credential. Railway connected tools
   expose variable names only. Do not extract tokens from browser internals or
   add general-purpose production execution endpoints as a workaround.
2. Inventory the owner's current Equifax and TransUnion originals/checkpoints.
   Confirm exact PDF hashes, dates and independent ground-truth counts before
   any paid operation; reuse valid checkpoints and recorded paid results.
3. Exercise index → one-batch banking → targeted repair where needed → merge →
   independent final audit for both bureaus. Record actual costs and misses.
   The owner must not perform raw JSON entry or backend benchmark QA.
4. Independently inspect real Mission Lane/Jefferson evidence. Synthetic
   relationship tests cannot establish the user's actual reporting issue.
5. Check the related-account UI on the authenticated mobile dashboard, using
   actual source pages. Only then close M4 and begin strategy/approval wiring.

## Following phases

M5: evidence-grounded action ranking and personalized strategy. M6: consumer
review and approval of an immutable package with a complete audit trail.
M7: PostGrid sandbox adapter, idempotent sends, authenticated provider events,
delivery/response tracking and follow-up preparation. M8: outcome intelligence
and hardening before outside consumers. Live submissions require the consumer's
necessary authorization; no provider variables alone constitute permission or
proof that a letter was mailed.
